## 2. A — 저장과 표시

**저장(확인).** 진술은 계약 출력 항목(`contract.outputs`) 한 곳에만 있다. edge는 `carries: [{node, item, used_at}]` 로 가리킨다. `check.py` 와 `build_viewer.py` 는 `tools/carries.py` 로 사본을 메모리에서 만든 뒤 일한다. 하위 graph 셋(con, thm, cc)의 edge는 subagent가 쓴 자기 진술을 그대로 갖는다(남의 진술 사본이 아니라 그 걸음의 결과라 지우지 않았다).

**묶음(확인).** `make_bundle2.py dedup` 은 node 진술 사본과 edge statement 사본을 빼고 '항목 사전'에 받는 항목을 하나에 한 번 넣는다.

| 묶음 | 앞 판 | 한 번만(들여쓰기 같게) | 한 번만(JSON 한 줄) |
|---|---|---|---|
| CC | 35,031 | 35,104 | 32,881 |
| THM | 17,176 | — | 16,284 |
| CON | 7,171 | — | 6,230 |

CC 묶음 32,881자의 구성: 원문 15,060, 항목 사전 5,130, 기호 표 4,310, 받는 edge(참조만) 3,956, 형식 지시 2,305, 자기 계약 1,593, 보내는 edge 498. **추론:** 앞 판에서도 남의 항목은 edge마다 한 번씩만 실렸다(받는 edge 하나가 한 보낸 node에서 온다). 그래서 중복은 처음부터 작았고, 묶음 크기는 원문 줄과 받는 항목의 양이 정한다. 앞 PoC 보고서 3절 1번의 추론("이름 참조로 바꾸면 줄어든다")은 틀렸다.

**화면(확인).** 생성기와 틀을 고쳤다.

- node 패널: 출력 항목(진술 + 원문 줄), 밖에서 받아 쓰는 항목(하위 graph의 external), 쓰는 기호(정의 + 원문 위치), 원문에 없는 걸음, 카드 번역(C), node의 원문 줄을 그 자리에 펼친다.
- edge 패널: 싣는 항목마다 보낸 node 제목, 진술, 그 항목의 원문, 받는 쪽이 쓰는 원문 줄을 펼친다. C 판처럼 "앞 node의 결과"만 싣는 edge는 그 node의 원문 줄을 붙인다.
- 글 안에 남은 `[NODE.item]`, `NODE.item`, 원문 label(`pert:selection` 꼴), 맨 위 node id는 패널을 그린 뒤 찾아 펼침(항목·원문 블록) 또는 그 node로 가는 단추로 바꾼다(세 겹까지).
- "쓰이는 곳"의 edge 번호와 받는 edge의 번호는 누르면 그 edge가 열리는 단추가 되었다. 근거의 "파일 줄" 문자열은 원문 블록으로 펼친다.
- **함께 고친 결함(확인):** 하위 graph(con, thm, cc)의 node에 배치 좌표가 없어 앞 PoC의 보기에서 모든 node가 한 자리에 겹쳐 있었다. 앞 PoC는 화면을 보지 않아 놓쳤다. 생성기가 좌표 없는 node에 edge의 깊이로 자리를 준다(`auto_layout`; 저장된 좌표가 있으면 건드리지 않는다).

감사 방법과 한계: 패널의 글 마디에서 펼침·단추·원문 블록·수식 밖에 남은 위의 꼴과 `<code>` 를 센다. 패널 자신의 이름(edge 패널 제목의 자기 id)은 뺐다. 지도 위의 상자와 edge 이름표에는 짧은 이름이 보이지만 누르면 패널이 열리므로 결함으로 세지 않았다. 하위 graph의 앞 판 edge가 쓴 지역 항목 이름(`abs_bound` 같은 것)은 같은 자리에 그 edge의 진술 전체가 있으므로 세지 않았다. 감사는 꼴 찾기라 이 꼴에 들지 않는 맨몸 이름은 놓칠 수 있다.

시험: `check.py` move5 오류 0·경고 2, move4 오류 0·경고 11(전과 같음). `test_viewer.py` 3개, `test_check.py` 1개, `test_output_contracts.py` 2개 실패는 고치기 전 HEAD 판에서도 같은 수로 실패한다(HEAD를 따로 풀어 `test_viewer.py` 를 돌려 같은 3개 실패를 확인; 나머지 둘은 HANDOFF 4절의 기존 기록과 같은 수). 경로 시험 통과. `build/move4.html` 도 새 틀로 다시 만들었다(자료는 그대로).

\* (나)는 답이 글로 돌아와 작성 세션이 파일로 옮겨 적었다(`B-na-CON.out.json`, 들여쓰기만 다름). 그 옮겨 적기는 작성 세션의 문맥을 약 5k 토큰 더 썼다.

**확인한 것.**
- 같은 조건 두 번(67,867 / 68,999)의 차이는 2%다. 측정은 재현된다.
- (나)는 (가)보다 30% 적다. (다)는 CON과 DC를 따로 연 합(149,317)보다 41% 적다.
- 품질 차이: (다)의 하위 graph가 조금 작다(CON 8→6, DC 10→9). DC를 따로 연 것과 함께 연 것 모두 같은 누락 의존("깊이 $q$ prefix가 주어지면 자식 가지가 조건부 독립")을 찾았다. (나)는 원문에 없는 걸음을 더 잘게 표시했다(10건).

**추론 (고정분의 정체).** subagent 토큰은 차례마다 그때까지의 문맥 전체를 다시 세는 합으로 보인다. 지시 → 묶음 읽기 → 쓰기 → 보고의 3–4 차례마다 시스템 문맥 S가 다시 들어간다. 두 점에 맞추면: (가) ≈ 3S + 2·묶음 + 2·산출 ≈ 69k, (나) ≈ 2S + 묶음 + 산출 ≈ 48k. 여기서 S ≈ 17–18k(시스템 프롬프트 + 도구 정의)가 나온다. "고정분 60k"는 대부분 **S × 차례 수**다. 묶음을 직접 주면 읽기 한 차례가, 답으로 받으면 쓰기 한 차례가 빠진다. 여럿을 한 agent에 맡기면 S를 나눠 낸다. 생각(thinking) 토큰이 이 합에 어떻게 들어가는지는 확인하지 못했다.

**추측.** (나)와 (다)를 함께 쓰면(묶음 여럿을 지시문에 넣고 JSON 여럿을 답으로) vertex당 25–30k까지 내려갈 수 있다. 도구가 전혀 없는 agent 종류는 이 세션에 없었다(Explore는 도구를 갖되 쓰지 말라고 한 것). 결정 5는 바꾸지 않았다.

## 4. C — 원문 참조("구조만") 방식

THM을 같은 정보 상태(`move5.contract-only.json`)에서 다시 열었다. 형식 지시 `format_structure.md`: node는 원문 줄 범위와 카드 id만 갖고 진술을 쓰지 않는다. LLM은 경계, 의존(어느 줄에서 쓰는지), 원문에 없는 걸음만 쓴다. 묶음에 THM 범위의 카드 8장(id, 제목, math, 원문 줄, uses, children)을 더했다.

| | 앞 PoC THM | C THM |
|---|---|---|
| subagent 토큰 | 84,618 | 77,996 (−8%) |
| 묶음 | 17,176 | 21,500 (카드 5,478 포함) |
| 산출 | 29,814 | **11,068 (−63%)** |
| 안쪽 node | 10 | 9 (그중 6개가 카드와 맞음) |
| 상위 수정 요청 / 누락 의존 | 4 / 4 | 2 / 2 |
| author_filled | 22 | 17 |
| check (사본에 넣어) | 오류 1 (X_EXT 닿는 면), 경고 1 | 오류 1 (같은 것), 경고 0 |

두 판 모두 같은 것을 놓친 것으로 찾았다: marker 계수 $-\delta$ 의 출처, THM 기호 목록의 `v_N`. 닿는 면 오류 1은 두 판이 같다. 묶음을 만든 뒤에 앞 PoC가 THM에 X_EXT 입력을 더했기 때문이다(확인).

C 판은 $\kappa(S)\ne0$ 의 근거($m_d-jm_{d+1}\ne0$)를 원문에 없는 걸음으로 직접 적었다. 앞 PoC에서 열린 채로 둔 항목이다. 이 근거는 확인하지 않았다.

**판정(추론).** 추측("원문을 다시 쓰는 출력이 비용의 큰 부분")의 앞 절반은 맞다. 출력은 크게 줄었다. 뒤 절반은 틀렸다. 출력 18.7k자(약 7k 토큰)가 줄어 두 차례에 걸쳐 약 14k가 빠져야 하는데, 묶음이 4.3k자 늘었고 실제로 준 것은 6.6k다. 비용의 주된 항은 3절의 S × 차례 수다.

**맞지 않는 곳(확인).** 생성 보기는 C 판 edge를 "내용 미작성"으로 표시한다. SPEC 5–6절은 edge가 자기 statement를 가져야 완결로 보기 때문이다. C 판에서 edge의 내용은 "보낸 node의 원문 줄"이다. 규격에 이 뜻을 더해야 C 판이 완결 판정까지 갈 수 있다([제안], 아래 5절). C 판은 `move5.json` 에 넣지 않았다. 비교용 보기 `C-view.html`(+ `C-view.json`)만 이 폴더에 있다.

## 5. 근본 원인에 대한 제안 (사용자 판정 전)

1. **[제안] 차례 수 줄이기.** 여는 작업을 "묶음을 지시문에 넣고, JSON을 답으로 받는" 한 차례 호출로 한다. 생성·검사는 작성 세션의 스크립트가 맡는다. 측정상 30%. 여러 vertex를 한 호출에 묶으면 S를 나눠 내 더 준다(41%). 결정 5와 충돌하는 부분(한 agent가 여럿)은 사용자 판정 대상이다.
2. **[제안] 카드를 구조의 출처로 쓰기.** THM 범위에는 이미 카드 8장이 증명을 s1–s5, s2.s1, s2.s2로 나눠 두었다. C 판 node 9개 중 6개가 카드와 맞았다. `x:decor-product-difference`, `x:decor-tree-sampling` 카드는 앞 PoC가 "놓친 의존"으로 찾은 둘(곱 차이 부등식, tree 표본 규칙)을 이미 담고 있다. 카드의 `children`·`uses`·원문 줄로 하위 graph의 뼈대를 기계로 만들고, LLM은 그 뼈대의 빈 곳(카드에 없는 의존, 원문에 없는 걸음)만 채우면 생성 자체가 줄 수 있다(추측). 이 갈래는 카드를 고치지 않고 읽기만 한다.
3. **[제안] 규격: 원문 참조 node와 edge.** node `lines`(+ `card`)가 진술을 대신하고, 안쪽 node에서 나오는 edge의 내용은 "보낸 node의 원문 줄"로 정의한다. 그러면 C 판도 완결 판정을 받을 수 있다. SPEC 7.7절 끝에 적었다.
4. **묶음 크기 기준(앞 PoC C7)은 고쳐야 한다.** 긴 증명은 원문만으로 원문 절반을 넘는다. 원문 대비가 아니라 "원문 + 받는 항목 외의 덧붙임" 비율로 재는 편이 맞다(추론).

## 6. 비용 (작성 세션)

정확한 단계별 값은 얻지 못했다. 이 후속 작업 전체에서 작성 세션의 문맥이 234,926 → 392,987(+158k)로 늘었다. 앞 보고서를 쓴 분 일부가 들어 있다. 대부분은 보기 고치기(틀·생성기 읽기와 수정)와 브라우저 감사다. subagent 다섯 번의 합은 363,014 토큰이다.
