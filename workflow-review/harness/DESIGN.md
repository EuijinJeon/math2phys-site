# 그래프 생성·수정 기록 하네스 설계안 0.1

2026-11-17 · 상태: 초기 설계 + 로컬 파일럿 구현. 실제 지원 범위는 README.md 참고

## 목표와 범위

일차 목표는 그래프를 생성하고 수정하는 절차를 명확히 파악하는 것이다. 매 작업의 입력, 실행, 산출물, 선택 근거와 변경을 남겨 사용자가 작업 과정을 재구성하고 그래프에서 질문할 수 있게 한다. 완전 자동 생성이나 동일한 LLM 응답 재현을 첫 목표로 삼지 않는다.

대상은 증명지도와 업무 검토 지도 모두다. 도메인별 그래프 형식·검사기는 유지하고 공통 작업 기록을 그 바깥에서 수집한다. 기존 PROCEDURE.md는 제작 회고, UPDATE-PROCEDURE.md는 운영 절차의 참고 자료다. 그 안의 명령·브랜치·게시 예시는 현재 실행 지시가 아니다.

## 세 가지 자료의 관계

1. **대상 그래프:** 논문 증명 또는 업무의 내용을 설명한다. node ID는 내용상의 단위다.
2. **작업 기록:** 대상 그래프를 어떤 자료로 어떻게 만들거나 수정했는지 기록한다. step ID는 작업상의 단위다. 한 step이 여러 node/edge를 수정할 수 있다.
3. **검토 그래프:** 작업 기록을 사용자가 읽기 쉬운 계층으로 보여 준다. 여러 tool call을 하나의 step으로 묶을 수 있으며, 묶음의 기준과 포함 event ID를 보존한다.

작업 기록을 기준으로 검토 그래프를 생성한다. 검토 그래프를 편집해 과거 실행 사실을 바꾸지 않는다. 사용자의 정정은 새 annotation과 revision으로 연결한다. 대상 그래프의 수정은 새 run 또는 기존 run의 새 attempt로 수행한다. 하네스 규칙을 바꾸는 피드백은 별도의 규칙 버전으로 다음 run에 적용한다.

## 작업 한 건의 단위

사용자 요청 한 건을 run으로 둔다. run은 요청 원문 참조, 신규/수정/설명만의 구분, 대상 그래프·노드·선, 시작 commit 및 미커밋 변경의 스냅샷, 적용 하네스·도메인 규칙 버전, 도구/실행 환경 버전, 기록 수집 범위를 가진다. 원본 요청에 비공개 내용이 있으면 공개용 요약과 분리한다.

step은 검토 가능한 결과를 하나 만드는 단위다. 모든 명령을 별도 step으로 만들 필요는 없다. 다만 하나의 명령이 원문 위치와 기존 지도 목록을 함께 출력하면 같은 call ID에 두 output ID를 연결한다. 두 번 실행한 것처럼 그리지 않는다. 다른 step의 결과를 소비하면 정확한 output ID를 참조한다. 단순히 앞뒤에 실행됐다는 이유로 데이터 의존 관계를 만들지 않는다.

## 기본 작업 흐름과 입출력

| 단계 | 입력 | 필수 출력·기록 |
|---|---|---|
| SCOPE 요청·대상 고정 | 요청, 기존 지도와 작업 상태 | 목표, 대상 ID, 생성/수정 유형, 완료 조건, 기준 버전 |
| READ 자료 확보 | 목표, 원문·기존 node 참조 | 실제 읽은 파일 버전·행 범위·반환, 미열람·잘린 범위 |
| DESIGN 그래프 설계 | 읽은 근거, 기존 그래프 | node 분해/유지 이유, node별 입력·변환·출력·조건, edge별 전달 항목과 근거, 생략·보충 |
| EDIT 변경 적용 | 설계안, 기준 그래프 | 변경 전후 JSON, 영향받은 node/edge ID, 패치와 내용 해시 |
| CHECK 내용·구조·화면 확인 | 변경 그래프와 생성물 | 검사 종류별 호출·결과, 실패·수정·재검사 연결, 미실시 항목 |
| DELIVER 저장·전달 | 검사 결과, 게시 범위 | commit, 전달 파일·URL, 게시한 경우 배포 ID와 공개 확인 결과 |

순서는 고정된 일방통행이 아니다. READ 추가 조회, DESIGN 재분해, CHECK 실패 후 EDIT로 돌아가는 반복을 보존한다. 새 시도는 attempt ID로 구별한다. 설명만 요청했다면 EDIT와 게시는 skipped이며 이유를 남긴다. 구조 검사 통과, 내용 검토, 실제 화면 확인을 하나의 성공 상태로 합치지 않는다.

## 단계별 기록 계약

실행 전에 LLM이 step.started를 남긴다: 목적, 완료 조건, 입력 참조, 예상 작업, parent step. 이 시점의 계획은 이후 사실 기록과 구별한다.

하네스는 tool.started/tool.finished를 자동 수집한다: provider call ID, step/attempt ID, 도구명, 정확한 인자 또는 보안 처리된 인자 참조, 작업 위치, 시작·종료 시각, 결과 참조, 종료 코드·도구 오류·중단 상태. 지원하지 않는 도구는 수집 불가로 명시한다. LLM이 직접 쓴 명령 요약을 자동 수집 로그로 표시하지 않는다.

실행 후 LLM이 step.finished 또는 step.blocked를 남긴다: output ID, 짧은 근거 기반 선택 설명, 사용한 evidence ID, 영향받은 대상 graph/node/edge, 남은 불확실성, 다음 단계에 넘길 output ID. 내부 사고 전문은 수집 대상으로 요구하지 않는다. 판단 요약의 종류는 agent_report이며 도구 관찰과 구별한다.

파일 자료는 path만으로 식별하지 않는다. commit+path 또는 저장한 스냅샷의 SHA-256과 보관 위치를 붙인다. 읽기 범위와 출력 잘림 여부도 기록한다. 해시만 있고 원본을 확보할 수 없으면 재실행 가능이라고 표시하지 않는다.

## 최소 자료 구조

- manifest.json: run ID, 요청 참조, 기준 버전, 환경, 수집 모드와 coverage, 완료 상태.
- events.jsonl: 추가 기록만 하는 사건 목록. event ID, run/step/attempt ID, type, actor, 기록 시각, 발생 시각(알 수 없으면 null), 참조 ID, payload.
- artifacts/: 허용된 입력 스냅샷, 반환, 그래프 변경 전후, 패치, 검사 결과. 크면 파일로 보관하고 event에는 참조만 둔다.
- annotations.jsonl: 사용자 정정·질문과 설명 수정. 원래 event를 덮어쓰지 않는다.
- review.json: event와 annotation에서 만든 검토 지도. 기존 workflow-review 형식으로 변환한다.

실제 raw 기록은 기본적으로 로컬 비공개 보관하며 Git에 자동 추가하지 않는다. 공개용 발췌는 별도 export에서 만들고 허용된 필드·파일만 포함한다. 현재 공개된 과거 발췌 승인을 미래의 모든 로그 공개 승인으로 확대하지 않는다.

## 출력 연결과 그래프 투영

output 참조는 `{run_id, step_id, output_id}`로 고정한다. 다음 입력에는 `from_output`과 사용 범위/필드를 둔다. 외부 원문처럼 앞 단계가 생산하지 않은 입력은 artifact 참조다.

- data 선: 실제 output 참조를 소비하며, 전달 내용과 사용 근거를 표시한다.
- sequence 선: 실행 순서만 표시한다. 자료 전달 미확인을 명시한다.
- note 선: 같은 호출의 다른 출력, 사후 설명, 제한 사항을 표시한다.

검토 지도 각 node에는 계획, 관찰된 호출, 작성자 판단, 검증 결과를 나눠 표시한다. 누락된 도구 반환은 unknown, 실행되지 않은 계획은 planned/skipped, 중단은 interrupted로 남긴다. observed 하나로 전체 step의 타당성을 승격시키지 않는다. coarse/fine 이동은 같은 event 범위를 유지하며 자식에서 상위 node로 복귀한다.

## 그래프 피드백 처리

사용자가 node·edge를 지정하면 먼저 대상이 내용 그래프인지 작업 검토 그래프인지 식별한다.

- 설명 요청: 관련 사건·자료를 읽고 근거와 한계를 답한다. 설명 보강은 annotation으로 기록한다.
- 작업 사실 정정: 기존 event를 보존하고 반증/정정 근거를 추가한다.
- 내용 그래프 수정: 새 요청 run에서 기준 그래프 → 근거 → 변경 → 검사 → 전달을 기록한다.
- 향후 절차 변경: 하네스 규칙의 패치와 버전을 기록한다. 과거 run의 규칙 버전을 소급 변경하지 않는다.

기존 node/edge의 생성·수정 step을 찾아갈 수 있도록 run/step ID와 변경 전후 버전을 연결한다. 삭제·분해된 ID는 이전 ID와 새 ID의 대응표를 보존한다.

## 수집 방식과 구현 순서

1. **수동 파일럿:** 위 계약으로 생성 1건·수정 1건을 기록한다. 가능한 provider 로그를 별도 대조한다. 이 단계는 agent_report 중심이며 자동 수집이라고 부르지 않는다.
2. **자동 수집 어댑터:** 먼저 로컬 명령 호출을 감싸 정확한 인자·반환·파일 버전을 저장한다. 이후 읽기·편집·브라우저·외부 도구를 연결한다. 기록 경로 밖에서 실행된 호출의 누락을 coverage로 표시한다.
3. **검사기와 변환기:** 사건 쌍과 입출력 참조, 변경·검사 연결을 검사하고 기존 검토 UI 데이터를 만든다.
4. **피드백 연결:** 검토 그래프의 질문이 annotation 또는 새 run을 만들도록 연결한다. 첫 버전은 질문 복사와 수동 run 시작으로 충분하다.

## 첫 파일럿의 합격 기준

새 소형 그래프 생성 1건과 해당 그래프의 edge 수정 1건을 대상으로 한다. 각 실행은 이 설계의 규칙 버전을 고정한다.

- 모든 변경 node/edge에서 생성·수정 step과 입력 근거로 이동할 수 있다.
- data 화살표마다 출력 ID와 소비 입력을 추적할 수 있다.
- 도구 호출·반환 쌍, 실패 후 재시도, 출력 잘림·누락을 구별할 수 있다.
- 읽은 자료의 해당 버전을 다시 열 수 있다. 접근 불가면 그 사실이 보인다.
- 구조 검사 실패를 넣은 파일럿에서 수정 전 실패와 수정 후 통과가 둘 다 남는다.
- 게시 성공을 파일 생성 성공으로 대신하지 않는다. 게시하지 않았으면 미게시로 기록한다.
- 검토 그래프의 설명을 고쳐도 raw 사건이 변하지 않는다.
- 담당자가 기록만으로 사용 자료, 변경 이유의 보고, 실제 변경, 수행/미수행 검사를 설명할 수 있다.

## 현재 상태

로컬 명령 래퍼, 기록 검사기, 별도 검토 JSON/HTML 변환기와 생성·수정 파일럿을 구현했다. 전체 도구의 자동 수집, 기존 공개 지도 형식 통합, 독립 세션 시험은 후속 범위다. 이번 설계 작업 이전의 실행을 새 규약으로 기록한 것처럼 소급 생성하지 않는다. 구현·검사 방법과 한계는 README.md에 있다.
